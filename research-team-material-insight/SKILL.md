# 研究团队技术合作价值分析

将材料解读为“技术合作价值分析”，而非论文、演讲或逐页内容摘要。围绕以下问题形成洞察：

1. 团队的持续研究主线、技术定位和所解决的核心问题是什么？
2. 哪3至5项成果最能证明其独特能力、技术突破和可迁移价值？
3. 这些成果改变了什么技术范式，仍有哪些证据或工程边界？
4. 哪3至4项具体技术最适合作为合作切入点，能解决什么业务问题？

不要写成老师观点转述、宣传稿、逐篇论文罗列或宽泛项目建议书。

## 输入与边界

- 将用户提供的PPTX、PDF、DOCX、论文、报告、会议纪要、演讲稿或文本作为主要事实来源。
- 按文件类型调用对应的PPTX、PDF或DOCX处理能力。处理演示文稿和PDF时必须查看渲染页，不能只依赖文本抽取；涉及图表判断时核对原图、坐标、图例和图注。
- 沿用对话中已明确的目标场景、读者、交付形式和材料共享方式；只有缺失信息会实质改变技术判断时才提问。
- 用户仅提供关键词、人名或机构名时，说明需要材料支撑；只有用户明确要求补充外部背景时才联网扩展，并与原始材料分开使用。
- 不把未来方向、业务示例或合作设想写成团队已验证的成熟能力或既有项目。

## 分析流程

### 1. 建立内部证据表

- 提取团队身份、研究主题、问题定义、方法机制、实验范围、量化结果、工程基础、限制与未来方向。
- 为候选判断记录页码、行号、图表位置或可靠视频时间戳，供内部核验；没有时间戳时不得编造。内部定位不等于成稿必须公开引用。
- 分析图表时查看渲染图，优先采集能证明机制或结果的原图。

### 2. 研究方向定位

先用一句话给出“团队聚焦什么、推动什么演进、解决什么核心瓶颈”的定位，再用一段说明其连续研究脉络。

- 不要并列堆砌技术名词，如“研究RAG、Memory和Agent”。
- 优先表达能力方向和问题，例如“聚焦智能体长期记忆，推动从知识检索走向经验推理”。
- 身份、职称、成员分工和项目归属只使用材料明确支持的事实。

### 3. 筛选核心成果

默认保留4项，允许3至5项。每项候选成果按以下顺序判断：

1. **独特性：** 是否体现区别于一般研究团队的方法、数据、评测或工程积累？
2. **问题与突破：** 是否清楚说明过去为什么难以解决，以及其机制改变了什么能力？
3. **证据强度：** 是否有实验、消融、量化结果或可验证工程事实？
4. **迁移价值：** 是否能映射到目标场景的具体技术问题？
5. **合作可操作性：** 是否能收敛为算法、机制、数据、训练、评测或原型？

- 合并机制相近、解决同一问题或业务价值重复的技术点。
- 基础设施规模、开源星标、工具数量和单项榜单通常只作成果证据；只有基础设施本身形成难以替代的训练、评测或执行闭环时才单列。
- 不因论文名称或项目数量多而逐项罗列。

每项成果必须回答：解决什么问题、核心创新在哪里、改变了什么能力、合作上有什么意义。默认使用以下结构：

### [成果名称]

**核心价值：** 说明其解决的长期问题，以及推动技术从什么状态向什么状态演进。

**关键技术突破：** 说明差异化机制；避免“使用LLM”“引入Agent”“使用Graph”等泛化表述。

**实验论据：** 给出能支持上述判断的实验、消融、量化结果或工程验证。

**合作意义：** 说明可迁移的业务能力或技术问题；证据不足时明确为待验证假设。

### 4. 判断技术范式变化

在成果后用一个短模块提炼真正的技术演进：

```
过去： [主流模式及瓶颈]
突破： [团队提出的关键能力或机制]
未来： [由材料支持的演进方向]
```

不要把“提出一个新模型”本身当作范式变化。只有当成果重新定义了知识、记忆、推理、规划、评测或执行等模块的角色和工作方式时，才突出这一层判断。

### 5. 形成合作价值分析

默认推荐3至4个方向。每个方向必须建立在前文已证明的能力上，并指向一个具体技术问题，而不是“大平台”“生态”或“联合中心”。

#### [具体技术方向]

**技术能力：** 前文已验证的团队方法或能力。

**可迁移场景：** 与用户目标业务的具体结合点。

**具体合作技术：** 拟共同研究或验证的算法、机制、数据、训练方法、评测或执行原型。

**解决问题及价值：** 合并说明当前瓶颈和预期业务价值，不重复拆分。

在资源研判阶段，不主动添加指标、里程碑、验收口径、项目边界或复杂风险控制；用户明确要求立项方案时再补充。

### 6. 区分事实、判断和建议

- **材料事实：** 原始材料直接说明或实验验证的内容。
- **能力判断：** 基于多项事实的保守推断。
- **合作建议：** 面向目标场景提出的技术切入点。
- **参考示例：** 仅在有助理解时使用，并明确不是团队已有成果。

### 7. 强制技术具体性

先写最能区分该团队的技术机制和结果，再补必要背景。不要用普及性知识、行业常识或宽泛趋势占据成果主体。

- 每个核心判断至少包含以下五项中的三项：具体问题对象、差异化机制、证据结果、适用边界、迁移场景。
- 对每个成果标题、核心价值和综合判断执行“名称替换测试”：去掉团队、项目和技术名称后，如果仍可套用于大多数研究团队，则判定为泛化表达，必须重写。
- “提升效率和准确性”“推动技术持续演进”“具有重要应用价值”“为企业智能体提供支撑”“形成完整技术闭环”“具备广泛应用前景”等表述不得单独作为结论；必须继续说明具体提升对象、实现机制、证据和场景价值。
- 优先写“对象 + 机制 + 结果/价值”，例如：“RoM以推理先验识别因果、时间和比较类信息需求，再用证据探针组合长期记忆中的分散证据，可迁移到依赖历史故障轨迹的网络根因分析。”
- 删除不影响技术判断的通用背景段。读者看完每项成果后应能回答：“这支团队具体做了什么，是如何做到的，为什么不是任何团队都能这样描述？”

## 写作与证据规则

- 直接陈述技术判断，不反复使用“老师认为”“材料展示”“从材料可以看出”等转述腔。
- 使用自然、克制的中文，避免宣传语、夸张比喻、反问和模板化过渡语。
- 标题和小标题要完整表达主旨；短观点使用“[小标题]：[完整判断]”的形式，例如“以推理需求驱动记忆调用：先判断所需因果、时间或比较信息，再定向组合历史证据。”
- 每项技术成果优先使用一张能直接支撑机制或结果的原图；无合适图片时不强行插图。
- 内部证据表保留来源位置。只有原材料会随成稿共享或用户明确要求时，正文才提供页码、文件引用或行号；否则去除分享页码及截图中的无意义页码。

## 默认输出

### 技术合作价值分析报告

使用 [references/report-pattern.md](references/report-pattern.md)：

1. 研究方向定位。
2. 3至5项核心成果洞察，默认4项。
3. 技术范式判断。
4. 合作资源价值分析与3至4项具体合作方向。

### 月报或聊天观点

- 先用一句总起句概括团队技术主线和合作价值。
- 默认4点，严格基于材料事实。
- 每点使用主旨完整的小标题，格式为“**[小标题]：** [判断]”；避免含义模糊的短标签。

### Word文档

用户要求Word报告时：调用DOCX处理能力，使用标题、分级标题、正文、少量原图和必要表格；每个技术大点优先配图与“实验论据”；完成渲染并逐页检查中文字体、图片、图注与分页。除非用户要求，不交付中间文件。

## 交付前检查

按照 [references/quality-checklist.md](references/quality-checklist.md) 完成检查。任何关键项未通过时，不得交付。

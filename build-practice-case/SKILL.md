# Build Practice Case

把真实工作过程和成果整理成可宣传、可复用、可评审的优秀实践案例。让方法、流程或工具成为主角；具体实例只负责证明其有效性。

## 1. 明确任务边界

开始前确认以下信息：

- 案例对象：要宣传的方法、流程、Skill或小工具是什么？
- 案例用途与受众：内部推广、经验交流、优秀实践申报还是管理汇报？
- 输入材料：过程记录、规则文件、原始需求、成果文档、截图、数据或用户反馈有哪些？
- 价值重点：用户最希望突出什么；这只是优先级，不代表必须凑齐所有价值类型。
- 输出形式：默认Word；当用途明显偏向现场汇报、用户提到演示需求或PPT可能更合适时，询问是否改为PPT。

只询问会实质影响内容或交付形式的缺失信息。材料足以支持合理判断时直接推进，并明确假设。

## 2. 建立证据台账

先分析材料，不要直接写稿。建立内部证据台账：

| 字段 | 内容 |
|---|---|
| 候选判断 | 准备在案例中表达的结论 |
| 证据类型 | 事实、能力判断、业务建议或包装元素 |
| 证据内容 | 原始材料、量化结果、规则或真实输出 |
| 来源位置 | 文件名、页码、段落、规则行号或截图位置 |
| 边界 | 已验证、合理推断、示例或待验证 |
| 候选价值 | 流程、创新、业务、质量、复用或其他价值 |
| 可视化方式 | 真实截图、表格、流程图或无需配图 |

严格区分：

- **事实证据：**原始材料直接说明或实际结果证明的内容。
- **能力判断：**由多项事实支持的保守判断。
- **业务建议：**面向下一步应用提出的方案，不写成既有成果。
- **包装元素：**标题、摘要、流程图、对比表、标注和版式，不作为事实证据。

不得补造界面、指标、用户评价、实施范围或效果。可以重新组织和突出真实信息；生成的解释性图表必须标注“示意图”。

## 3. 找到案例主线

用一句话写出案例主线：

> 面对[具体角色在具体环节遇到的问题]，通过[关键流程或机制]，形成[可验证成果]，并带来[材料实际支持的核心价值]。

主线必须回答：

1. 原来的工作为什么难，现有做法具体卡在哪里？
2. 新方法改变了哪个关键步骤、判断或协作关系？
3. 与常见做法相比，差异化机制是什么？
4. 哪些真实输出或结果能够证明价值？
5. 这套实践如何被复用，下一步还应改进什么？

如果主线去掉工具、方法、对象名称后仍可套用于多数案例，继续收窄。

## 4. 筛选价值与亮点

不要预设价值类型、亮点数量或截图数量。先从材料中识别实际存在的价值，再选择有证据、最有区分度的内容重点展开。价值可以只成立一种，也可以同时成立多种。

可识别但不限于：

- **流程价值：**减少重复劳动、沟通损耗、遗漏或不稳定环节，使工作路径可复用、可检查。
- **创新价值：**提出新的机制、约束、组合方式或判断方法，而不只是使用热门技术。
- **业务价值：**帮助特定角色完成更好的判断、协作或交付，并指向具体业务问题。
- **质量价值：**提高输出的一致性、准确性、可追溯性或可控性。
- **复用价值：**把一次性经验沉淀为可重复执行的方法、规则或模板。

按以下标准选择通常3至5个亮点；材料不足时可以更少：

1. 是否解决了具体问题；
2. 是否有差异化机制；
3. 是否有规则、过程、输出、数据或反馈支持；
4. 是否对目标受众重要；
5. 是否适合通过实例或图片说明。

每个亮点至少写清四项中的三项：

- 具体对象或问题；
- 差异化机制；
- 实际结果或可观察变化；
- 适用边界。

删除“提升效率”“赋能业务”“形成闭环”“智能化升级”等没有对象、机制和证据支撑的孤立表达。

## 5. 按四部分写案例

只保留以下四个一级部分。控制子标题数量，避免把案例拆成说明书。

### 一、当前痛点

从实际角色和任务切入，写清：

- 谁在什么场景下遇到困难；
- 困难发生在哪个决策、协作或交付环节；
- 现有做法为什么不够；
- 由此带来什么具体影响。

不要用大段行业背景代替真实问题，也不要把“不了解技术”“没有时间”写成空泛抱怨；要说明因此难以识别、判断或交付什么。

### 二、分析和对策

先解释问题为什么发生，再按步骤写清实践方法：

1. 输入什么材料或信息；
2. 如何识别和筛选关键内容；
3. 如何形成核心判断；
4. 如何把判断转化为成果；
5. 如何检查证据、边界和表达质量。

在本部分设置一个完整的“具体实例及实现过程”子节，展示：

> 输入材料 → 关键处理步骤 → 中间判断 → 最终输出

实例只用于证明方法，不得让读者误以为该实践只能用于这一对象或只能生成这一类成果。说明哪些步骤可复用、哪些内容取决于实例。

### 三、成果

先概括这套实践能够形成的通用成果类型，再展示实例成果。只写材料实际支持的价值，不设置没有内容的流程、创新或业务价值小节。

重点说明：

- 实践带来了什么可观察变化；
- 哪个机制改善了原有做法；
- 对使用者、质量、复用或业务判断产生了什么价值；
- 哪些结果已被证据证明，哪些仍是定性判断。

有量化数据时使用准确数字；没有时采用可核验的定性描述，不虚构百分比、时长或评价。

### 四、改进点

选择2至4项真正影响下一阶段效果的问题。每项用一段说明：

- 当前还欠缺什么；
- 下一步准备如何改；
- 改进后希望增强什么能力。

避免为每项机械重复“不足—优化—目标”，也不要把未来设想写成已完成成果。

## 6. 设计截图和图表

让图片证明关键设计和价值，不要为了版面固定放3张或其他数量。

优先选择：

- 能证明独特机制或质量控制规则的真实规则截图；
- 能展示关键步骤、判断过程或前后变化的过程图；
- 能证明最终成果内容和质量的真实输出截图；
- 能帮助理解差异的对比表；
- 能说明实例如何实现的局部放大图。

截图选择遵循：

1. 每张图只证明一个主要观点；
2. 优先截取最有区分度的规则和结果，不截宽泛介绍；
3. 必要时裁剪、放大、拼接和标注，但不改变原意；
4. 真实截图与生成示意图明确区分；
5. 图注写明“这张图证明什么”和“来自哪里”；
6. 多张图表达同一观点时合并或删除。

允许对成果进行表达包装，包括重组内容、设计标题、突出重点、制作流程图、对比表和摘要卡片。不得把重新绘制的内容伪装成真实产品界面或既有成果。

## 7. 生成交付物

- 默认使用文档创建与检查流程生成`.docx`。
- 只有用户确认选择PPT后，才使用演示文稿创建与检查流程生成`.pptx`。
- 保持专业、克制的语言，减少口号、夸张类比、普及性背景和重复结构。
- 标题同时体现实践对象、关键输入或核心价值，避免“基于材料的案例”这类弱标题。
- 交付前读取[质量检查清单](references/quality-checklist.md)，逐项检查并修改。

## 8. 完成标准

只有同时满足以下条件才算完成：

- 案例对象始终是方法、流程或工具，实例没有取代案例主体；
- 四个一级部分完整，且“分析和对策”包含清晰步骤和完整实例；
- 至少一种核心价值被具体说明并有证据支持，不为凑结构虚构其他价值；
- 核心判断能够回到证据台账；
- 图片数量由关键设计和证据决定，且每张图有明确证明目的；
- 成果包装与事实证据的边界清楚；
- 改进点具体、简洁、不重复；
- Word或PPT已完成结构、内容和视觉检查。
